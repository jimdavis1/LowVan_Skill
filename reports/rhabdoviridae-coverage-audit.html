What the Rhabdoviridae annotation module actually covers

We built software that names the proteins in rhabdovirus genomes. This is the test of how well it works — run against every rhabdovirus genome in the public database, not against the handful of examples it was built from.

What is being tested, in plain terms

Rhabdoviruses are a family of RNA viruses that includes rabies. A rhabdovirus genome is small — usually five genes in a fixed order — and public sequence databases hold tens of thousands of them. The problem is that the protein names attached to those sequences were written by thousands of different submitters, so the same protein appears under dozens of different spellings, and many carry no useful name at all.

The software being tested here, LowVan, replaces those inconsistent names with one controlled set. Given a raw genome sequence it works out which proteins are present, where each one starts and stops, and what each should be called. It works in three steps:

  1. Pick the right rulebook. Rhabdoviruses are diverse enough that one set of rules cannot cover them all, so they are split into four groups, each with its own rulebook — we call one of these a module. The genome is compared against a small set of known reference genomes to decide which module applies. A genome too unlike any reference gets no module, and nothing further happens to it.
  2. Search for each protein. Each module knows which proteins it expects. For each one it holds a set of statistical patterns — profiles — built from many real examples of that protein. A profile captures which amino acids are conserved and which vary, so it can recognize a protein that is only distantly related to any single example. The genome is searched with every profile the module holds.
  3. Fix the boundaries and name it. Where a profile matches, the software extends the match outwards to the real start and stop signals in the DNA, then attaches the standard name for that protein.
The five core proteins. Almost every rhabdovirus genome carries the same five, in the same order, and this report refers to them by their conventional single-letter names: N (nucleocapsid, wraps the genome), P (phosphoprotein, part of the copying machinery), M (matrix, structural), G (glycoprotein, the spike on the virus surface), and L (the large polymerase that copies the genome). A genome that is complete and correctly annotated should show all five.

How this was built, and who decided what

This module was built by the author of the annotation system working with an AI assistant. The division of labor was deliberate and it is the reason the result is checkable: the curator set the rules and made every judgement call; the assistant did the mechanical work and had to show its evidence.

The work ran as a loop, and the loop is the method:

  1. Sort the existing names. Pull every protein the public database holds for the family, count how the names are actually spelled, and decide which spellings mean the same protein. This is where the real errors get made, because a wrong decision here is invisible afterwards — the pipeline will happily build a confident profile out of two unrelated proteins that happened to share a label.
  2. Group, align, and build profiles. Mechanical, and left to the software.
  3. Curate the alignments by hand. Also not automatable. The curator opens them and fixes them.
  4. Install it and run it against the entire family. Not against the examples it was built from — against every genome the database holds.
  5. Find the largest remaining gap and test why it exists. Not guess why. The phosphoprotein section below is this step working exactly as intended: the expected explanation was poor sequencing, the test said otherwise, and the real cause implied a completely different fix.
  6. Fix that one thing, and go back to step 2.

The rules the curator set

These were laid down as standing constraints, most of them after watching the assistant do something subtly wrong. Each one is now enforced in code or written into the build instructions, so the next virus family does not relearn it:

Never group sequences below 60% identity

Below that, one profile stops representing one protein. When data is thin, require fewer examples per group — never accept looser matches into a group.

Drop a virus group rather than guess at it

If there are not enough sequences to build real profiles, the group is dropped and the reason recorded. Naming proteins by their position in the genome, because you cannot recognize them any other way, is not acceptable.

Vague names must never pool sequences

“Hypothetical” and “uncharacterized” are not protein names. Proteins carrying them are split by actual similarity into separately numbered groups, so that when one is eventually identified it can be renamed on its own without disturbing the rest.

Machine-suggested citations are kept separate

A literature reference proposed by the assistant is stored in its own field and never mixed with references a human has read. A plausible-looking citation that nobody checked is indistinguishable from a verified one unless the two are kept apart.

Report against what you claim to cover

Scores are reported per module, over the virus groups that module was designed for. Averaging in groups nobody built a rulebook for measures ambition, not performance.

Never keep a reference you cannot follow through on

A reference genome that lets a virus in, when no profile can then describe it, converts an honestly rejected genome into a badly annotated one. Five such references were removed.

Record the near misses

A genome that resembles a reference but then matches no profile still gets a record of which group it resembled and how strongly. That is real information and it was being thrown away.

Reassemble split genomes before scoring

Where a virus stores its genome in several pieces and the database files each piece separately, the pieces are rejoined first — and only when the count matches what that virus should have.

Anything mechanical becomes a script; anything requiring judgement stays written instructions. Every analysis in this report is now a program that can be re-run on another virus family — including the ones first done by hand, such as cutting out the region between two genes to look for a missing one, and measuring whether protein ends are landing where they should. What deliberately stayed as written guidance is the part that does not transfer: which genes sit next to which, how many reference genomes are worth maintaining, which protein ends are genuinely trimmed, and whether a virus group has enough data to model at all. Those are read and decided by a person each time.
Two habits did most of the work. First, test the explanation, do not assume it — the largest gap in this module had an obvious-sounding cause that turned out to be wrong, and acting on the obvious cause would have achieved nothing. Second, a measurement that cannot fail is not a measurement — this module scored 95% on its development set both before and after a change that found 120 missing proteins. Every number in this report comes from genomes nobody curated by hand.

How the test was run

The public database holds 25,237 rhabdovirus records, but that number overstates the diversity badly: well-studied viruses like rabies are sequenced thousands of times over, and most records are fragments rather than whole genomes.

So the records were first grouped by similarity, putting any two genomes that are 95% identical into the same group. That gives 1,983 groups. One representative from each group was annotated, so every genuinely distinct kind of genome gets one vote and rabies does not drown out everything else. 1,356 representatives were long enough to be worth annotating.

Why not just test on known examples? Because the software was built from known examples, and it recognizes those almost perfectly. On the eight-genome reference set used during development it scores 95% — and that score did not move at all across a change that added 471 new profiles and found 120 previously-missed proteins. Testing against the whole database is the only way to see what the software misses in genomes nobody curated by hand.

Which genomes never get looked at?

259 of 1,356 genomes (19%) resemble no reference genome closely enough to be assigned a module, down from 315. Every one records the same reason, and there are no crashes left in the set. These genomes never reach the protein search at all, so no improvement to the profiles can help them.

The improvement from 315 is not better matching — that step does not use the profiles. It is that genomes which were assigned a module but then matched none of its profiles now match something, plus four references added for virus groups that had contributed sequences to the profiles yet could not get a genome through the door.

The obvious fix is to add more reference genomes, and the first thing to establish is how many of these 259 are even eligible:

This corrects an earlier conclusion. A previous version of this report said the curve was flat, that 200 of the unmatched genomes were one-offs, and that adding references was not worth it. That comparison had been run with settings that under-sampled the matches, finding 7,283 where a complete run finds 32,076. Re-run properly, using the same matching settings the software itself uses, the answer is the opposite. How many references are worth maintaining is still a judgement call — every one is a permanent obligation — but it is now a judgement made against the right numbers.

Separately, four references were added on a different test: virus groups that had contributed sequences to the profiles and still could not get a single genome assigned. One went from zero to 11 out of 11 on all five core proteins. Five more were added and then removed again — they let in 14 genomes that came back with the polymerase named and nothing else, which is exactly the failure the 119 above would reproduce.

How many results are trustworthy?

Alongside the annotator there is a separate quality checker. It re-reads each finished genome and raises a flag wherever something looks wrong — an expected protein absent, a protein much shorter or longer than that protein should ever be, the same protein named more times than it should occur, or a sequence containing so many unreadable bases that no software could annotate it reliably.

It ran over the 1,118 genomes that had at least one protein named. The other 265 have nothing to check, and the checker declines them rather than inventing a verdict. The raw result is a 49 / 51 split, clean against flagged — but that number is misleading, because two of the three kinds of flag say nothing about the annotation software:

verdictgenomesshare
clean, nothing flagged54448.7%
flagged only for unreadable bases in the sequence22720.3%
flagged only because one gene is split in two100.9%
flagged for a substantive reason33730.1%

A sequence that is more than 1% unreadable is a verdict on the sequencing, not on the annotation. Setting those aside, 70% of the genomes checked are annotated acceptably and 30% have something genuinely wrong.

A correction worth recording. The quality check was moved onto a richer output format partly on the argument that the simpler format miscounts genes that are split into fragments. That argument was wrong — the richer format does not fix it either. A polymerase broken in two still appears as two separate proteins, which trips both the “too short” flag and the “named too many times” flag on the same 203 genomes, counting one problem twice. The richer format is still the right choice, but for a different reason: the simpler one cannot represent certain unusual gene types at all, and would silently score them as non-existent in virus families that have them. Rhabdoviruses have none, so the shortcut appeared to work here and would have failed quietly elsewhere.

Where the missing phosphoproteins actually were

The natural assumption was that P was missing because those genomes were poorly sequenced. That assumption was testable, and it was wrong.

P sits between N and M in the genome. So we took the 115 genomes where N and M were both found but P was not, cut out the stretch of DNA between them, and translated it in all six possible reading frames to see whether a phosphoprotein gene was sitting there unrecognized:

the stretch between N and M was present   115/115   typically ~1000 bases
it contained a plausible gene             115/115   typically ~296 amino acids
that gene resembled known phosphoproteins 109/115

more similar to a sequence NO profile was built from   85
more similar to a sequence a profile WAS built from     0

Zero. Every missing gene was present, full length, and recognisably a phosphoprotein — and not one of them resembled any sequence the existing profiles had been built from. The genes were never missing. The profiles simply did not cover that part of the family.

The discarded sequences were the important ones. When profiles are built, sequences are grouped with their close relatives and each group becomes one profile. Sequences too unusual to join any group were being set aside — and those are precisely the sequences a profile set most needs to cover, because they represent the corners of the family furthest from the well-studied examples. Re-grouping the set-aside sequences among themselves, at the same strictness but allowing a group to form from as few as two members, produced 331 new profiles and took the total from 484 to 955. The strictness was never relaxed; only the question of how many examples are needed before a profile can be built at all.

Translating those stretches also turned up 21 phosphoproteins that appear in no public protein record at all. They were added back into the collection so the discovery survives the next rebuild.

A cut site that was not a cut site

The glycoprotein G is made as a longer precursor and then trimmed: a short leader sequence is cut off, leaving the mature protein. The software is told which ends of a protein are cut ends, because a cut end is not marked by the normal genetic start and stop signals and must not be extended to look for one.

Mature G was declared to have both ends cut. Only the front end is. The back end of the mature protein is the back end of the precursor — the trimming happens only at the front. With the back end wrongly marked as cut, the software never looked for the stop signal and simply ended the protein wherever the search happened to stop:

back end of mature Gbefore after
lands on the correct stop signal583 / 973952 / 971

The correction cost nothing — mature G was found in exactly 974 genomes before and after. It gave 369 of them a correct ending.

This is worth checking in every virus family and checking hardest in families whose proteins are made as one long chain and cut into many pieces. A precursor cut into three products has six cut ends, and every one wrongly declared drifts on its own and compounds along the chain.

Does the naming actually converge?

This is the point of the whole exercise. Both the public database and this software attach a name to every protein. The difference only becomes visible when you count how many different names are in use as you look at more and more genomes.

The 1,062 genomes named by both were shuffled into random order 200 times, and the count of distinct names was tracked as genomes accumulated:

A controlled vocabulary levels off, because each new genome reuses names the earlier ones already established. Free text keeps climbing, because every new submitter spells the same protein a new way. This software reaches 95% of its final vocabulary after 254 genomes; the public database needs 938, and is still climbing at the right-hand edge.

A 12.8-fold reduction — and the shape matters more than the ratio. The rising curve has no plateau to reach, so the gap between the two widens with every genome added.

What the exercise was worth

Running the software against an entire virus family, rather than against the examples it was built from, found: four bugs in the annotation program, one rulebook not worth keeping, a genome-reassembly step without which an entire virus group reads as broken, five reference genomes worth removing, a set of discarded sequences that turned out to hold the answer to the largest remaining gap, and a mis-declared cut site that had been quietly misplacing the end of a protein in 40% of genomes.

None of it was visible from the eight-genome development set, which this software passed at 95% throughout — before and after a change that added 471 profiles and 120 phosphoprotein calls. Testing against your own examples tells you the software recognizes them. Only a whole-family run tells you what it misses in genomes nobody curated.

Terms used here

Module

One rulebook, covering one group of related viruses that share the same gene layout. There are four for the rhabdoviruses.

Profile

A statistical pattern for one protein, built from many real examples. It records which amino acids are conserved and which vary, so it can recognize distant relatives that no single example would match.

Routed

Matched a reference genome closely enough to be assigned a module. A genome that is not routed is never searched for proteins.

Annotated

Came back with at least one protein identified and named.

N, P, M, G, L

The five proteins almost every rhabdovirus carries, in genome order: nucleocapsid, phosphoprotein, matrix, glycoprotein, and the large polymerase.

Mature protein

What remains after a protein has been trimmed. G is made as a longer precursor with a leader that gets cut off.

Cut end

An end of a protein produced by trimming rather than by the genetic start and stop signals. The software must be told which ends these are.

Exemplar

One genome chosen to represent a group of near-identical genomes, so that heavily sequenced viruses do not dominate the result.
